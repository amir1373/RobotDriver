# RobotDriver

Embedded STM32 firmware for a networked robotic motor driver/controller. The project combines Ethernet Modbus TCP, RS-485/USART Modbus RTU, FreeRTOS task scheduling, SPI flash support, encoder feedback, and timer-driven PWM motion control on an STM32F407 microcontroller.

## Overview

RobotDriver appears to have been built as a distributed robotics or industrial automation controller: each board reads a DIP-switch address, configures a node-specific Ethernet identity, exposes command/status registers over Modbus TCP, and drives a motor axis through GPIO direction control and TIM5 PWM pulse generation. One address mode switches the firmware into a Modbus RTU master role for polling PLC-style remote inputs and writing relay outputs.

The repository is preserved as a legacy embedded engineering project. The original firmware structure, generated STM32CubeMX files, IAR EWARM project files, middleware, and driver layout are intentionally retained so the project remains authentic and buildable in its original toolchain.

## Hardware Architecture

- MCU: STM32F407VGTx / STM32F407VGT6, Cortex-M4F, LQFP100.
- Clocking: 25 MHz external HSE, PLL system clock configured to 168 MHz.
- Ethernet: RMII interface with LAN8742 PHY and LwIP static IPv4 configuration.
- RS-485 / serial: USART1 with TX/RX and a direction-control GPIO, using DMA reception and IDLE-line frame detection.
- Motor interface: GPIO motor enable and direction pins, TIM5 CH1 PWM pulse output, TIM2 encoder interface.
- Nonvolatile storage: STM32 internal flash EEPROM emulation and W25Qxx SPI flash driver.
- Local IO: DIP-switch address inputs, alarm/input pins, relay output, and communication/fault/status LEDs.
- Debug/programming: SWD enabled.

## Firmware Architecture

The code is primarily STM32CubeMX-generated C with user firmware in the `USER CODE` regions of `Core/Src/main.c`.

- `ModbusTCPTaskFunc`: waits for address initialization, resets the Ethernet PHY, initializes LwIP, then services the Modbus TCP server.
- `MotorControlTaskFunc`: runs the motor pulse-generation loop, PID-assisted speed shaping, PWM start/stop handling, and final position persistence.
- `ModbusRTUTaskFunc`: when DIP address selects RTU-master mode, polls slave discrete inputs and mirrors relay commands to Modbus coils.
- `GovernerTaskFunc`: initializes SPI flash, reads DIP switches, selects node mode/addressing, maps Modbus holding registers to motion commands, and handles EEPROM reset/update behavior.
- Interrupts: USART1 IDLE interrupt performs DMA receive framing for Modbus RTU; TIM5 PWM callbacks count motor pulses; TIM6 provides HAL tick timing and periodic encoder updates; Ethernet interrupt is routed to the HAL ETH driver.

## Build Instructions

This project was generated from `RobotDriver.ioc` with `ProjectManager.TargetToolchain=EWARM V8.50` and currently includes IAR project files.

1. Install STM32CubeMX or STM32CubeIDE with STM32Cube FW_F4 V1.28.1 available.
2. Install IAR Embedded Workbench for ARM compatible with the EWARM project format.
3. Open `EWARM/Project.eww` in IAR Embedded Workbench.
4. Select the `RobotDriver` configuration.
5. Build, flash, and debug using an ST-LINK or compatible SWD probe.

The `.ioc` file is preserved for CubeMX inspection/regeneration. If regenerating code, keep user code regions intact and review generated middleware paths before committing.

## Engineering Notes

- The firmware uses DIP switches for deterministic node identity. Addresses map to the last byte of the static IP address and also select whether the device behaves as an axis controller or RTU master.
- Motor motion is command-register driven. The upper controller writes target sign, target angle, speed, and update bits into Modbus holding registers; firmware computes pulse count and direction, drives PWM, then updates completion/status registers.
- Position retention is implemented with internal flash EEPROM emulation. This is useful for legacy systems without dedicated EEPROM, but flash endurance and page-transfer behavior should be considered during frequent updates.
- Ethernet startup is sequenced from a FreeRTOS task after GPIO-based PHY reset, which matches the board-level dependency on the external LAN8742 PHY.
- USART1 receive handling uses DMA plus IDLE detection, a common embedded pattern for variable-length serial protocols such as Modbus RTU.
